# PR Body Rules

PR 설명은 사람이 변경을 이해하고 리뷰할 수 있도록 쓴다. 첫 문단에서 무엇을 왜
바꿨는지 밝히고, 이어서 핵심 구현 방식과 적용 범위를 설명한다. 작업 일지를 옮기지 않는다.

## 설명에 남길 내용

- 결과와 이유를 먼저 쓴다. 새 기능이면 무엇을 만들었고 어디에 쓰려는지,
  버그 수정이면 어떤 상황에서 무엇이 잘못됐고 어떻게 달라지는지 적는다.
  이유가 자료에 없으면 지어내지 말고 확인된 목적과 변화만 쓴다.
- 구현 방식은 그 결과를 이해하는 데 필요한 수준으로 설명한다. 파일·함수·토큰 경로를
  나열하는 대신 무엇을 공통화했는지, 어떤 동작을 처리했는지 쓴다.
- 구현만 끝났는지 실제 사용처에도 적용했는지 구분한다. 기존 동작이나 호환성 설명은
  적용 범위 또는 전환 제약을 이해하는 데 필요할 때 남긴다.
- 요구사항과 다른 구현, 동작에 영향을 주는 제약, 후속 조치, 중요한 검증 한계는
  간결하게라도 반드시 남긴다. 짧게 쓰려고 리뷰 판단에 필요한 사실을 빼지 않는다.
- 본문 길이와 항목 수는 변경 복잡도에 맞춘다. 무엇을·왜·어떻게를 각각 별도 제목으로
  만들거나 정해진 줄 수에 맞출 필요는 없다.

## 덜어낼 내용

- 커밋 구성표, 조사 순서, 시행착오, 에픽에서 몇 번째 PR인지 같은 작업 이력은
  기본적으로 넣지 않는다. 최종 diff의 결과를 기준으로 설명한다.
- 세부 치수, 전체 옵션, 내부 분기, 호출부 개수, 커밋 해시는 리뷰 판단을 바꾸는
  근거일 때만 쓴다. 긴 근거는 문서나 코드 링크로 연결하고 본문에는 결론을 남긴다.
- 중점 리뷰 항목은 판단이나 주의가 필요한 사항만 고른다. 모든 구현 내용을
  번호를 붙여 리뷰 요청으로 바꾸지 않는다.
- 선행 PR 관계는 의존 대상과 필요한 조치로 설명한다.
  예: `#413의 stack PR입니다. #413 병합 시 rebase가 필요합니다.`
  추가 의존성이 실제 병합 순서나 조치를 바꾸면 그 조건도 남긴다.
- 같은 사실을 작업 내용, 관련 링크, 기타 요청 사항에 반복해서 풀어 쓰지 않는다.
- 검증 사진처럼 아직 제공할 수 없는 자료를 위한 섹션을 새로 만들지 않는다.
  자료 부재가 검증 한계라면 검증 항목에서 짧게 밝힌다.

## 템플릿

저장소 템플릿을 다음 순서로 찾는다.

1. `.github/pull_request_template.md`
2. `.github/PULL_REQUEST_TEMPLATE.md`
3. `.github/pull_request_template/*.md`
4. `.github/PULL_REQUEST_TEMPLATE/*.md`

템플릿이 있으면 섹션 구조, 체크박스, 안내 문구를 유지한다. 해당 없음은 `N/A`로
표시한다. 정해진 섹션 안에서도 핵심 설명을 먼저 쓰고 불필요한 하위 제목은 늘리지 않는다.
템플릿이 없으면 다음 구조를 출발점으로 삼되 변경에 필요한 섹션만 사용한다.

```markdown
## 작업 내용

<무엇을 왜 바꿨는지. 핵심 구현 방식과 적용 범위.>

## 검증

<실행한 검증과 결과. 중요한 미검증 범위 또는 실패.>

## 관련 이슈

<티켓 또는 선행 PR 링크와 필요한 조치.>
```

## 관련 이슈 추론

브랜치명, 커밋 메시지, diff에서 `#123`, `fixes #123`, `closes #123`,
`[A-Z][A-Z0-9]+-[0-9]+` 패턴을 찾는다. 찾을 수 없으면 `N/A`를 사용한다.

## 작성 후 점검

- 첫 문단만 읽어도 무엇을 왜 바꿨는지 알 수 있는가?
- 코드 경로나 작업 이력을 몰라도 구현 방향과 적용 범위를 이해할 수 있는가?
- 세부 설명마다 리뷰어가 알아야 할 이유가 있는가?
- 중복을 덜어내면서 요구사항 차이, 제약, 필요한 조치와 검증 한계는 보존했는가?
