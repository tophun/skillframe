# 인라인 코멘트 문장 루브릭

`code-review-writer`가 코멘트를 쓰고 스스로 채점할 때 쓰는 유일한 기준. 오케스트레이터는 이 파일의 절대 경로를 writer에 넘긴다. 다른 곳에 사본을 두지 않는다.

## 3단 구조

각 코멘트는 **① 무엇이 문제인지 → ② 왜 문제인지 → ③ 어떻게 고치는지(suggestion)** 순으로 쓴다. 전문 용어보다 동료가 바로 이해할 표현을 쓴다.

> 예) "이 `useEffect`는 `console.log`만 실행하는 디버그용 코드입니다(①). 실제 기능엔 영향이 없으니 병합 전에 지우면 좋겠습니다(②). 아래 suggestion으로 블록을 통째로 지울 수 있습니다(③)."

짧게 쓴다. 배경 설명이 길어지면 문장 대신 근거 라인 번호를 준다.

## 리뷰 도구 사정은 쓰지 않는다

코멘트는 코드 얘기만 한다. suggestion을 못 붙인 사정, 판단을 미룬 이유, 리뷰 범위 제약은 읽는 사람에게 아무 정보도 주지 않는 사족이다.

| 쓰지 않는다 | 대신 |
| --- | --- |
| "수정 범위가 350-359행까지 걸쳐 있어 suggestion 대신 예시로 적어둡니다" | 범위를 `start_line`~`line`으로 앵커해 suggestion을 붙인다. 정말 불가능하면 코드블록만 붙이고 사족 없이 끝낸다 |
| "어느 쪽이 맞는지는 판단이 필요한 부분이라 아래 suggestion에는 넣지 않았습니다" | "스펙상 A가 맞다면 X, B가 맞다면 Y입니다"처럼 선택지만 제시한다 |
| "리뷰 도구 한계로…", "제 권한으로는…", "확인해보지 못했지만…" | 지운다 |
| "AI가 검토했습니다", "Generated with Claude Code" | 지운다 |

## 어색한 한자어 대신 개발자가 실제로 쓰는 말

| 쓰지 않는다 | 대신 |
| --- | --- |
| "`error` useEffect도 같이 **발화**해서" | "같이 **실행돼서**" · "같이 **동작해서**" · "**트리거돼서**" · (UI면) "**같이 떠서**" |

`발화`는 불이 붙는다는 뜻이거나 언어학에서 말하기를 가리키는 단어라 코드 동작 설명에 맞지 않는다. 이벤트·훅·핸들러가 도는 상황은 "실행된다 / 동작한다 / 트리거된다 / 같이 뜬다"로 쓴다. 다른 표현도 마찬가지로, 문어체 한자어보다 팀에서 실제로 주고받는 말을 고른다.

## 어조

- 단정 대신 근거. "틀렸습니다"가 아니라 "이 경로에서는 X가 되는데, 의도한 게 맞나요?"
- 확실한 버그는 확실하게. 근거가 있으면 질문형으로 눅이지 않는다.
- 백틱 안 코드 식별자·경로·수치는 **절대 바꾸지 않는다.**
- 존댓말 평서체. 이모지·불릿 남발 금지.
