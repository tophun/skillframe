# PR Tone Rules

PR 제목과 본문은 사람이 한눈에 이해하도록 두괄식으로 쓴다. 결론을 먼저 말하고
이유와 필요한 근거를 붙인다. 간결함은 정보 선별의 결과이며, 설명 생략이 목적은 아니다.

## 문장 방식

- 한국어로 담백하고 명확하게 쓴다. 과장, 사과, 변명, 마케팅 표현은 피한다.
- 첫 문단은 연결된 짧은 평서문으로 쓴다. 병렬 변화나 검증 결과는 목록을 쓸 수 있다.
- 각 문단과 목록 항목도 핵심 변화부터 쓴다. 배경을 길게 설명한 뒤 결론을 붙이지 않는다.
- 코드 식별자는 필요할 때 정확히 쓰되, 그것만으로 설명을 대신하지 않는다.
  `토큰을 읽는 컴포넌트`보다 무엇을 만들었고 어떤 역할을 하는지 말한다.
- `작업`, `수정`, `개선` 같은 흐린 말로 끝내지 않는다. 누가 무엇을 어떤 상태로
  사용할 수 있게 되는지 구체적으로 쓴다.
- 문장을 억지로 명사형으로 끊거나 `추가했습니다`만 반복하지 않는다.
- 확인한 범위만 적는다. 설명을 자연스럽게 만들려고 원인이나 효과를 만들어내지 않는다.

## 예시

아래는 문장과 정보량의 예시다. PR 번호나 구현 내용을 다른 PR에 그대로 쓰지 않는다.

장황한 배경:

> 디자인 시스템 에픽의 네 번째 PR입니다. #413 위에 쌓인 stacked PR이라
> base가 feat/UG-459입니다. #413이 머지되면 base를 바꿔 주세요.

필요한 관계와 조치:

> #413의 stack PR입니다. #413 병합 시 rebase가 필요합니다.

구현 용어에 치우친 설명:

> tokens/component/button을 읽는 첫 Design System Component입니다.
> 세 컴포넌트는 아직 아무 화면도 쓰지 않고, SolidButton은 수정하지 않았습니다.

역할과 적용 범위가 드러나는 설명:

> 디자인 시스템의 공통 컴포넌트로 Button, IconButton, Spinner를 추가했습니다.
> 버튼 스타일은 공통 토큰으로 관리합니다. 이번 PR에서는 컴포넌트만 구현했으며,
> 실제 화면 적용은 후속 작업으로 진행합니다.

짧게 써도 남겨야 하는 요구사항 차이:

> Button variant는 Figma 이름에 맞춰 yellow/gray/line을 유지했습니다.
> 티켓의 ‘색상명 미노출’ 조건은 충족하지 않으며, Figma와 코드의 이름 변경은 후속 작업입니다.

## 검증 표현

- 실행한 명령은 정확히 적고 결과를 간단히 붙인다. 기존 기록을 인용했다면
  이번에 직접 실행한 검증과 구분한다.
- 검증 범위를 이해하는 데 필요할 때만 테스트 수, 기기, 측정값을 덧붙인다.
- 중요한 미실행 검증은 `미실행`과 이유를 적는다. 이유를 모르면 확인되지 않았다고 쓴다.
- 실패와 남은 차이를 숨기지 않는다. 이전 버전의 통과를 최종 변경의 통과로 쓰지 않는다.
